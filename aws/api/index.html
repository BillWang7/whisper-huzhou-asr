Why ~15 seconds? A deliberate cost trade-off

This demo runs on a serverless AWS architecture built to cost close to nothing when no one is using it: the browser uploads audio straight to S3, which triggers a containerized Lambda function that runs the model and writes the result to DynamoDB, while API Gateway serves the page and job status. Everything is defined as code (AWS SAM).

  • Fitting the model: Lambda has no GPU and caps memory at 3 GB, so the 769M-parameter model was converted to 8-bit (CTranslate2, 3 GB → 742 MB). On held-out test clips its error rate stays within about 1 point of the full model (news: 24.6% vs 23.8%).
  • Tuning: profiling traced an early accuracy loss to the audio preprocessing rather than the 8-bit weights, and benchmarking chose x86 over ARM processors (about 30% faster per clip).
  • The result: about 13 seconds per clip on 2 CPU cores (up to a minute if the site has been idle, while Lambda starts up), at about $0.0007 per transcription. An always-on GPU server would answer in about a second but cost about $590 a month.
* Baseline outputs are precomputed, not run live. They were generated once in advance by running the unmodified openai/whisper-medium on every test clip, with the same settings (language: Chinese, task: transcribe, same loop guard). The fine-tuned model's output is computed live every time you press Transcribe. Error rates are character error rate (CER): edit distance divided by reference length, ignoring punctuation, which can exceed 100% when the output is longer than the reference. The scores in the header are for the full-precision model. All featured and random clips are held out: none were used in training. Real-speaker sentences come from everyday dialogue and narration, so word choices the model renders differently count as errors even when the meaning is kept.
